I quattro principi fondamentali (P.O.U.R.) 📖

Percepibile 👀 (Perceivable)

Le informazioni devono essere percepibili dagli utenti.

Esempi pratici:
  • • Immagini con attributo alt
  • • Contrasto cromatico adeguato tra testo e sfondo

Utilizzabile 🎮 (Operable)

L'interfaccia deve poter essere utilizzata anche senza mouse.

Esempi pratici:
  • • Navigazione completa tramite tastiera
  • • Utilizzo del tasto Tab per spostarsi tra gli elementi

Comprensibile 🧠 (Understandable)

Contenuti e interfaccia devono essere chiari e prevedibili.

Esempi pratici:
  • • Uso corretto dell'attributo lang
  • • Comportamento coerente della navigazione
  • • Messaggi di errore chiari nei form

Robusto 🛡️ (Robust)

Il codice deve funzionare correttamente con tecnologie assistive.

Esempi pratici:
  • • Uso corretto dell'HTML semantico
  • • Utilizzo degli attributi aria-* quando necessario

L'Evoluzione Semantica: HTML vs ARIA 🧬

Proprio come un Pokémon si evolve per diventare più forte, l'HTML si è evoluto introducendo tag semantici che rendono superflui molti ruoli ARIA. La prima regola di ARIA è: se esiste un tag HTML nativo, usalo! Ecco un "Pokédex" delle equivalenze:

Elemento HTML Nativo
Ruolo ARIA Equivalente
<main>
role="main"
<nav>
role="navigation"
<header>
role="banner"
<footer>
role="contentinfo"
<aside>
role="complementary"
<section>
role="region" (se ha un nome accessibile)
<article>
role="article"
<form>
role="form"
<button>
role="button"
<a href="...">
role="link"

5

Le trappole del Team Rocket 🚀

Attenzione agli inganni! Il Team Rocket cerca sempre di sabotare l'accessibilità con scorciatoie e "trucchetti" che sembrano funzionare, ma che in realtà creano solo problemi agli Allenatori. Ecco le loro trappole più comuni:

pointer-events: none

Può rendere gli elementi inutilizzabili con il mouse pur restando nel flusso della tastiera.

flex order

Modifica l'ordine visivo ma non quello nel DOM, creando incoerenze per gli screen reader.

position: absolute

Se usato per spostare contenuti importanti può rompere l'ordine logico di lettura.

line-clamp

Taglia visivamente il testo ma il contenuto resta nel DOM.

Assenza di focus ring

Rimuovere l'outline del focus rende difficile capire dove si trova il cursore della tastiera.

Dimensioni fisse

Testi impostati in pixel possono causare problemi quando si utilizza lo zoom.

Font poco leggibili

Font decorativi o testi lunghi completamente in maiuscolo riducono la leggibilità.

aria-disabled="true"

Usare solo l'attributo ARIA senza disabilitare realmente l'elemento (es. omettendo l'attributo disabled nativo o non bloccando gli eventi click).

Minestrone di semantica

Mischiare semantiche native o abusare degli attributi aria- e role (es. <a role="button"> invece di un vero bottone). La prima regola di ARIA è: se puoi usare un elemento nativo, usalo!

Ignorare i pattern ufficiali

Inventare soluzioni "comode" per lo sviluppatore ma che violano la prevedibilità per l'utente. Segui sempre i pattern WAI-ARIA ufficiali per componenti complessi come tab, modali e menu.

Strumenti per testare l'accessibilità 🛠️

  • build
    axe DevTools Estensione per browser essenziale per scovare errori nel codice.
  • format_size
    Text Spacing Editor Testa come il layout risponde alle modifiche di spaziatura del testo.
  • devices
    BrowserStack Accessibility Toolkit Strumento completo per testare l'accessibilità su vari dispositivi.
  • fact_check
    Silktide Accessibility Checker Simula disabilità visive e controlla il contrasto e il codice.
  • insights
    Accessibility Insights Suite di Microsoft per test rapidi e approfonditi.
  • contrast
    Colour Contrast Checker Verifica che il contrasto tra testo e sfondo sia sufficiente.
  • waves
    WAVE Evaluation Tool Evidenzia visivamente gli errori di accessibilità direttamente sulla pagina.
  • keyboard_tab
    taba11y Mostra visivamente l'ordine di tabulazione (focus) degli elementi interattivi.
  • verified
    Siteimprove Accessibility Checker Analizza la pagina e fornisce spiegazioni dettagliate sugli errori.
